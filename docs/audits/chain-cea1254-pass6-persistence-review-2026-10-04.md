## F18: code identity across persistence

**Observed source.** [Incremental code write](../../crates/torus-state/src/incremental.rs#L306), [plain block commit](../../crates/torus-bridge/src/committer.rs#L83) and [EVM bundle batch](../../crates/torus-bridge/src/committer.rs#L257) all use `bytecode.bytes()`. [Database code reload](../../crates/torus-state/src/db.rs#L985) reads `CF_CODE` and constructs `Bytecode::new_raw`. [Code storage](../../crates/torus-state/src/db.rs#L776) documents hash-keyed bytecode but does not check key/value hash equality.

`Cargo.lock:5545` pins `revm-bytecode` 9.0.0. The cached dependency source at `/tmp/torus-cea1254-pass3-deps/revm-bytecode-9.0.0` was inspected locally: `src/bytecode/mod.rs:130` records input length before analysis; `:296` returns backing bytes; `:314` slices to original length; `:175` sends ordinary legacy code through analysis again. `src/legacy/analysis.rs:38` adds padding when required. This review did not download or independently revalidate the original archive checksum. These local definitions support the earlier finding's serialization mismatch; this is not an assumption about a different revm release.

**Qualification.** This is a DB round-trip issue, not exclusively a restart issue. A new execution context loading code from the committed DB can expose it in a later block during the same process lifetime. Not every program needs padding, and no fixed padding amount should be asserted. Original code containing legitimate trailing zero bytes must survive unchanged; a repair that trims zeros is not supported by the serialization contract. No Torus contract execution was performed here.

**Coverage read.** [The deployment test](../../crates/torus-evm/tests/evm_tests.rs#L199) asserts successful execution, an address and gas use, then discards `_bundle`; it neither persists the deployment nor checks loaded code. [Incremental root tests](../../crates/torus-state/src/incremental.rs#L603) primarily exercise account/storage roots. Account-root equality does not assert that the bytes under `CF_CODE[code_hash]` reproduce that hash: [the full EVM root](../../crates/torus-state/src/trie.rs#L50) uses account `code_hash` values.

**Recommended assertions.** For a normally deployed runtime that requires analysis padding, check exact original bytes, original length and hash immediately in the returned bundle, after each of the three persistence paths, in a subsequent call, and after closing/reopening RocksDB. Assert `keccak256(stored_code) == account.code_hash` and equal code-size results before and after the round trip. Include control cases with no padding and original trailing zeros. These assertions test observable code identity rather than merely comparing two root implementations that both trust the same stored hash.

## F19: configuration on normal restart

**Observed source.** [Startup](../../crates/torus-node/src/main.rs#L529) parses supplied genesis and takes its chain configuration before checking whether accounts already exist. The accounts check suppresses genesis initialization; it does not suppress configuration substitution. With no genesis path, [the fallback](../../crates/torus-node/src/main.rs#L550) uses [defaults](../../crates/torus-node/src/main.rs#L341). Genesis can also come from a TOML config file via [apply_config_defaults](../../crates/torus-node/src/main.rs#L287), so CLI omission alone does not imply fallback.

[ExecutionContext initialization](../../crates/torus-consensus/src/app.rs#L3785) receives epoch length and recipient addresses from the selected configuration. [Fee dispatch](../../crates/torus-bridge/src/native_executor.rs#L8259) passes those addresses into [reward crediting](../../crates/torus-economics/src/rewards.rs#L66). This supports configuration-dependent state evolution with identical ordinary activity. It does not mean all `ChainConfig` fee-ratio fields are honored by the reward distributor; that separate existing economics concern is outside this review.

[Boot activation configuration](../../crates/torus-consensus/src/app.rs#L3865) calls [configure_activation](../../crates/torus-state/src/running_hash.rs#L254), whose changed-definition branch deletes its stored running hash/checkpoints. That branch explicitly warns. The no-genesis branch explicitly logs default selection. Accordingly, the earlier word **silent** should mean acceptance without canonical mismatch rejection, not absence of diagnostics. An observed node/peer divergence is not claimed.

The parent applied these wording corrections to the pass-3 consolidated report during this review: omission from both CLI/TOML, available logs/warnings, and preservation of planned activation rollout in the remediation direction. Those changes correct audit prose; they do not repair node startup configuration handling.

**Specification mismatch.** [The CLI help](../../crates/torus-node/src/main.rs#L98) says genesis is required for first run. More explicitly, [the relaunch runbook](../ops/s442-relaunch/relaunch-runbook.md#L115) says genesis is ignored on later restarts. Source shows that only initialization is skipped; the file's configuration still controls the restart. The runbook should be corrected even before a broader configuration persistence change.

**Coverage read.** [chain_config_from_genesis](../../crates/torus-genesis/src/lib.rs#L818) checks parsing/mapping of a supplied genesis; it does not boot existing state without that file. [The activation rollout test](../../crates/torus-consensus/src/app.rs#L14811) intentionally permits enabling a future chain-wide activation at different preactivation heights. [The unverified-node test](../../crates/torus-consensus/src/app.rs#L15191) checks late activation behavior. Neither exercises omitted or substituted genesis through node startup. They also establish that an authorized activation upgrade is a supported behavior; a blanket prohibition on every configuration transition would conflict with those tests.

**Recommended assertions.** Use a nondefault chain with nonzero fee recipients, a short epoch schedule and enabled running hash. Close and reopen the same DB through the actual startup configuration resolution, supplying (a) identical genesis, (b) no genesis in either CLI or TOML, (c) identical TOML-provided genesis and (d) different chain configuration. Assert canonical config equality and preserved checkpoint history for normal restart, or explicit rejection before execution and before writing activation metadata. Compare the next ordinary fee-bearing block and the next epoch boundary against an uninterrupted reference. Keep the explicit planned activation-rollout case and assert its authorized transition behavior separately. Configuration identity must account for actual execution/consensus fields and distinguish local operator switches from canonical chain settings.

## F21: intact snapshot restore versus verification coverage

**Observed source.** [Snapshot creation](../../crates/torus-state/src/snapshot.rs#L88) invokes RocksDB Checkpoint; its documented operation includes all column families at one DB instant. [Verification](../../crates/torus-state/src/snapshot.rs#L111) recomputes plain EVM and full native roots and compares only their composite result to `metadata.state_root`. [NATIVE_ROOT_CFS](../../crates/torus-state/src/native_trie.rs#L47) contains seven families. It excludes nonces, sessions, queue, governance and market registry. [The EVM root](../../crates/torus-state/src/trie.rs#L58) trusts stored account code hashes; it does not independently validate every `CF_CODE` value. Metadata height, block hash, validator hash and CF count are read but not cross-checked against DB frontier/identity in this verifier. Restore calls verification first and [recursively copies snapshot files](../../crates/torus-state/src/snapshot.rs#L294), including files containing excluded families.

**Scope correction.** Omission from the verified root does not mean omission from the checkpoint or loss during an intact restore. No ordinary successful create/restore operation was found here that selectively drops those excluded rows. F21 remains a limitation on what `verified == true` establishes. The earlier excluded-state model demonstrates only projection coverage; it does not execute RocksDB, prove physical-corruption behavior or establish ordinary restart data loss. This review did not develop or execute snapshot alteration cases. Verification is also relative to supplied metadata, not an independent external chain identity anchor.

**Coverage read.** [create_snapshot_and_verify_passes](../../crates/torus-state/src/snapshot.rs#L365) uses two EVM accounts and root equality. [restore_from_valid_snapshot](../../crates/torus-state/src/snapshot.rs#L414) restores to a new directory and checks one account. [verify_detects_corrupted_snapshot](../../crates/torus-state/src/snapshot.rs#L387) and [restore_rejects_corrupted_snapshot](../../crates/torus-state/src/snapshot.rs#L442) change metadata's root; their names should not imply complete state-integrity coverage. [The integration lifecycle test](../../crates/torus-integration-tests/tests/snapshot_dos_keys.rs#L50) seeds EVM accounts/storage; its `column_family_count = 32` is accepted because no verifier assertion binds that field. It does not exercise populated native nonce/session/queue/governance/market families.

**Recommended ordinary-operation assertions.** Populate every authoritative family via supported operations, take a snapshot at a known durable applied height with execution quiesced, close/reopen the restored DB, and compare all authoritative rows byte-for-byte to the snapshot reference. Then continue ordinary operations and compare balances, pending next-height queue processing, market configuration, accepted session use and nonce allocation with an uninterrupted reference. Independently assert metadata block hash/frontier/validator set and chain configuration identity match the selected checkpoint. This catches accidental omissions while making clear that round-trip completeness and complete commitment coverage are different contracts. Do not add CFs to the consensus root casually: changing its input set is a protocol/root-definition change requiring its own compatibility plan.

## F30: applied marker and EVM mirror resync

**Observed source.** [The serial flush](../../crates/torus-consensus/src/app.rs#L2489) includes native overlay writes and applied height. [Serial EVM account resync](../../crates/torus-consensus/src/app.rs#L2558) follows it. The worker follows the same order at [its flush](../../crates/torus-consensus/src/exec_pipeline.rs#L426) and [resync](../../crates/torus-consensus/src/exec_pipeline.rs#L485). [resync_evm_accounts](../../crates/torus-state/src/incremental.rs#L431) writes hashed accounts and trie updates in [a later DB write](../../crates/torus-state/src/incremental.rs#L480). Both writes can succeed in an uninterrupted run; termination between them is sufficient for the reported consistency window.

Boot's [ensure_trie_built](../../crates/torus-state/src/incremental.rs#L131) calls a [nonempty hashed-account probe](../../crates/torus-state/src/incremental.rs#L143). [Replay](../../crates/torus-consensus/src/app.rs#L4227) starts after applied height. Neither reconstitutes the interrupted transient dirty-address list. [Default root routing](../../crates/torus-bridge/src/state_root.rs#L19) enables incremental computation. [Debug/oracle routing](../../crates/torus-bridge/src/state_root.rs#L51) detects disagreement, but detection is not boot repair. Stale off-by-default comments at app.rs:2554 and :3833 do not describe current routing.

**Clerical correction.** The pass-4 consolidated report originally linked this resync write to `incremental.rs#L517`, inside tests. The exact write is `#L480`; the parent corrected that link during this review. The change repairs the citation only and does not fix production behavior.

**Coverage read.** [resync_evm_accounts_repairs_native_post_commit_drift](../../crates/torus-state/src/incremental.rs#L909) establishes deliberate plain/mirror drift and explicit resync repair within one DB handle. It does not reopen the DB, pass boot initialization, advance an applied marker or prove automatic repair. [The EVM crash helper](../../crates/torus-consensus/src/app.rs#L15654) stops before the combined state flush and compares a rerun to clean execution. [The pipeline crash test](../../crates/torus-consensus/src/app.rs#L13718) injects failure before the worker write and replays from the old marker. Both cover different seams. Neither reaches successful marker write followed by omitted resync.

**Recommended assertions.** Add a controlled stop after successful serial/worker state-marker write and before resync. Start with a nonempty correct mirror; perform an ordinary native operation that credits a distinct EVM recipient. Close/reopen actual RocksDB and pass normal boot initialization. Assert correct recipient balance, unchanged durable applied height, and full/incremental root equality *before further execution*. Follow with unrelated activity and assert equality remains; touching the same recipient would hide inadequate recovery. Include existing/new recipient and empty-account/deletion materializations where supported. Exercise release/default routing as well as debug/oracle routing; debug detection alone cannot certify normal release behavior. A repair needs a durable stale/dirty indication or an atomic final mirror update. The existing [build_trie_to_cf](../../crates/torus-state/src/incremental.rs#L60) overlays plain rows and does not clear old hashed rows, so reusing it as a general repair requires separate deletion and consistency tests.

## F31: retention must protect replay inputs

**Observed source.** [Commit events](../../crates/torus-node/src/main.rs#L958) update the shared latest-height handle. [The background pruner](../../crates/torus-node/src/main.rs#L1169) passes that height into [maybe_prune](../../crates/torus-state/src/pruner.rs#L139); cutoff is `current_height - retention_blocks`. [prune_range](../../crates/torus-state/src/pruner.rs#L207) deletes bodies below the exclusive cutoff without consulting applied height. [Dispatch persistence](../../crates/torus-consensus/src/app.rs#L994) removes a manifest when the body joins that batch. Thus accepted retention can remove the durable body while execution still depends on it.

[Replay](../../crates/torus-consensus/src/app.rs#L1312) stops at a missing nonempty body, and [recovery source selection](../../crates/torus-consensus/src/app.rs#L1131) falls back to local `Durable` when no manifest remains. [Local materialization](../../crates/torus-consensus/src/app.rs#L5954) returns an empty missing-hash list on that body miss. [The fully-fed shortcut](../../crates/hotstuff_rs/src/committed_feed.rs#L105) does not compare native applied height; [tree gap scanning](../../crates/hotstuff_rs/src/block_sync/client.rs#L677) checks tree index entries rather than the separate execution-body CF.

**Qualifications.** This is an optional-pruning/recovery gap. Default archive mode is unaffected. Missing nonempty blocks are parked rather than silently marked applied. The retained committed datum and explicit later body delivery can allow recovery; permanent loss of all copies is not established. [The configuration reference](../configuration-reference.md#L35) presents retention as historical-data policy; unapplied inputs are not safely disposable historical data. The fix horizon must respect that distinction. Because deletion is exclusive, a safe applied bound can be `min(policy_cutoff, applied.saturating_add(1))`, conservatively handling absent/unreadable markers.

**Coverage read.** [prune_removes_old_bodies_and_receipts](../../crates/torus-state/src/pruner.rs#L340) tests deletion/retention and preserved headers but supplies no execution frontier. [prune_meta_persists_across_restart](../../crates/torus-state/src/pruner.rs#L460) reopens RocksDB to check pruning progress only. Despite its name, [crash_replay_runs_after_pruning](../../crates/torus-consensus/src/app.rs#L7434) adds a prune metadata key and replays empty blocks; it never invokes `StatePruner` or deletes a required body. [Commit-before-execute recovery](../../crates/torus-consensus/src/app.rs#L7716) relies on the body remaining intact. [Missing-body replay](../../crates/torus-consensus/src/app.rs#L7618) and [boot parking](../../crates/torus-consensus/src/app.rs#L7668) protect against skipping, while [late body injection](../../crates/torus-consensus/src/app.rs#L8147) demonstrates externally supplied repair rather than automatic rediscovery of pruned bodies.

**Recommended assertions.** Pause ordinary execution with several nonempty committed/dispatched heights above durable applied height, advance the real fed marker, and run the actual pruner with small positive retention and zero retention on an eligible interval. Assert every unapplied body or equivalent durable recovery datum remains. Close/reopen RocksDB without injected bodies, peers or operator repair; normal replay must reach the committed frontier and match an uninterrupted state's balances, nonces, receipts and roots. Include native and EVM body classes. Check the exclusive boundary at applied/applied+1 and preserve existing large-retention/archive tests. Missing/error applied-marker reads must not permit deletion beyond a proven safe bound. This combines components currently tested in isolation.

## Coverage limits and ordinary restore follow-up

The historical H02 two-directory-rename seam in [snapshot restore](../../crates/torus-state/src/snapshot.rs#L203) remains distinct from F21. Both intact DB copies can survive while the active path is absent between renames; [normal startup](../../crates/torus-node/src/main.rs#L523) creates/open that path. Existing valid-restore tests restore into a new path, so they do not verify replacement of existing state or recognition of `.old`/`.restoring` after interruption. Recommend a bounded intact-snapshot replacement regression that interrupts before/after each rename and requires ordinary startup to resume a valid selected DB or fail explicitly. This is a retained historical follow-up, not a sixth new finding or an executed crash experiment.

All recommendations above are test specifications, not added or passing tests. In-memory context recreation and source-pattern Python models cannot substitute for actual RocksDB close/reopen, exact process-termination seams or node startup configuration resolution. This pass establishes where current safeguards apply and where targeted correctness coverage remains missing; it does not certify the whole persistence subsystem.

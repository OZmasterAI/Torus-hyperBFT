# Torus chain correctness audit

Audited on 2026-10-04 at `cea1254e34625e6b09c58f794de8793b5c12713c`, branch `merge/item6-sync2`. This is a source audit of the checked-out chain, including the oracle, liquidation, resident-state and anti-spam integration. It is not an audit of a deployed network or a later branch revision.

**Result: seven source-supported findings warrant regression tests and fixes.** The most urgent are unbounded proposer-controlled execution gas, duplicate EVM fee credits, expired session authorization, and execution continuing after local storage failures. I would resolve these before a deployment handling valuable assets.

Per this directory's audit convention, findings remain candidates until reproduced by failing production-code tests. Four small executable Python counterexample models support the arithmetic and scan findings; they do not execute Rust, verify signatures, run consensus or reproduce a live exploit. Rust/Cargo, mold and sccache were unavailable on this machine's PATH. No Rust test suite, multi-validator simulation, storage fault injection or power-loss experiment was run. No production code was changed, no live chain was contacted, and nothing was committed or pushed.

| --- | --- | --- | --- |

## F01 Proposers can bypass execution gas bounds

**Evidence.** `crates/torus-consensus/src/app.rs:5062` (`check_proposal_data`) verifies the datum, native action count, ancestry, timestamp and native-body availability. `validate_block` at line 5320 repeats structural/ancestry checks. Neither establishes an allowed `evm_gas_limit` or `base_fee_per_gas`. The parent-link check at line 1452 does not constrain those fields either.

After consensus, `app.rs:1816` calls `validate_block_for_catchup`. In `crates/torus-bridge/src/validator.rs:102`, that selects `parent_header=None, skip_state_root_check=true`; the base-fee check requiring a parent is bypassed. Lines 147–156 construct the EVM environment directly from the submitted header. `crates/torus-evm/src/executor.rs:545` copies those values into revm.

The exact pinned dependency matters: revm-context 15.0.0 `src/cfg.rs:396` returns `u64::MAX` as its default transaction gas cap before Osaka. Torus explicitly selects Cancun at `executor.rs:267`. revm-handler 17.0.0 `src/validation.rs:149` checks this cap, then at line 210 compares transaction gas against the block limit supplied by Torus. This does not restore the intended 30M protocol limit.

**Impact.** A Byzantine proposer can submit an otherwise well-formed block with an enormous gas limit, zero base fee, and a signed transaction whose execution burns that gas. The regular mempool's stricter gas limits do not protect consensus against a proposer constructing its own payload. Honest validators can order the block before discovering its prohibitive execution cost. A zero base fee also removes the gas-payment barrier for this scenario. The exact stall duration and recovery behavior need runtime measurement.

**Regression test.** Build a valid child proposal, change only its gas limit and base fee, and recompute its hashes. Both header/body and full-proposal voting paths must reject it using a shared deterministic header rule. Test enforcement with a bounded long-running EVM transaction in an isolated fixture; do not run a near-`u64::MAX` workload on a live chain.

**Recommended fix.** Define and enforce protocol execution parameters before voting and on sync insertion, independently of RPC admission. In a consensus-then-execute design, derive or explicitly constrain fee/gas fields whose parent execution results may not yet exist. Add an executor-side deterministic bound as defense in depth.

## F02 EVM fees credit the priority component twice

**Evidence.** `crates/torus-evm/src/executor.rs:267` builds the standard mainnet revm handler with Torus precompiles. It does not replace beneficiary fee accounting. The pinned revm-handler 17.0.0 `src/post_execution.rs:69–88` credits the beneficiary with `(effective_gas_price - base_fee) * gas_used` under Cancun. Its archive SHA256 exactly matches `Cargo.lock`: `9f1eed729ca9b228ae98688f352235871e9b8be3d568d488e4070f64c56e9d3d`.

`crates/torus-bridge/src/proposer.rs:395` computes Torus fee revenue as the **full** `gas_used * effective_gas_price`. `app.rs:2142` seeds the native overlay from the EVM bundle, retaining revm's tip credit. At line 2303, Torus distributes the full fee again. `crates/torus-economics/src/rewards.rs:58–72` credits the unburned portions, and `staking.rs:1020` adds those credits to EVM account balances. There is no compensating subtraction of the already-paid tip in this path.

**Counterexample.** For a 21,000-gas transfer with base fee 1 gwei and effective price 2 gwei, the sender pays `42,000,000,000,000` wei. revm pays `21,000,000,000,000` wei to the beneficiary. At epoch zero, Torus additionally credits 90% of the full charge: `37,800,000,000,000` wei. Net supply increases by `16,800,000,000,000` wei instead of decreasing by the scheduled `4,200,000,000,000` wei burn. The difference is exactly the duplicated tip. The attached model evaluates this arithmetic.

**Regression test.** Execute and commit a tipped transfer through `ExecutionContext`, with distinct sender, beneficiary, treasury and dev-pool accounts. Sum spendable balances plus any reward liabilities before and after; assert the only supply change is the specified burn. Repeat with a registered proposer and a reverted transaction.

**Recommended fix.** Choose one owner for gas-fee accounting. Either have Torus distribute fees from a genuinely withheld amount, or retain revm's tip payment and exclude that amount from subsequent credits. Pin the intended burn/reward policy in supply-conservation tests.

## F03 Expired session keys remain authorized at execution

**Evidence.** `crates/torus-bridge/src/native_executor.rs:7665` converts block seconds to milliseconds when creating a session. Stored `expiry` is in milliseconds. In contrast, `crates/torus-consensus/src/app.rs:1998–2001` passes the unconverted header timestamp into `batch_verify_native_actions_cached`. At `crates/torus-types/src/eip712.rs:1228`, session authorization tests `timestamp <= session.expiry` directly.

RPC admission uses `validate_with_sessions` with milliseconds. Therefore ingress can correctly reject an expired key while consensus execution still authorizes it. Pre-vote validation intentionally defers individual action authorization to execution, so RPC rejection is insufficient protection against a proposer including such an action.

**Counterexample.** A session created at second `1791100000`, valid for 60 seconds, stores expiry `1791100060000`. At block second `1791100120`, it has expired, but `1791100120 <= 1791100060000` is true. The attached model checks both comparisons. Revocation is separate: a deleted session row will still be rejected.

**Regression test.** Store a real millisecond-expiry session, sign an action with its session key, include it after expiry, and execute through the actual committed-block path. Assert the action is skipped and does not alter balances/orders. Test any explicitly approved execution grace period at its boundary.

**Recommended fix.** Pass a clearly named millisecond timestamp into session verification, with checked/saturating conversion. Audit the legacy bridge proposer/validator callers too. Torus memory contains an older session-expiry fix discussion on another worktree; the reviewed revision still has the mismatch, so historical fix notes do not establish that this branch is fixed.

## F04 Storage faults can become divergent committed state

**Evidence.** At `crates/torus-consensus/src/app.rs:1875–1877`, **every** error from committed-block EVM validation is logged and execution continues. `crates/torus-evm/src/executor.rs:611` maps a revm database error to an internal EVM error; it is not restricted to invalid user transactions. Root calculation in `crates/torus-bridge/src/validator.rs:193` can also return storage errors after successful execution.

The failed EVM section leaves an empty bundle and zero computed fee revenue. The rest of the block can still run, and `app.rs:2714–2772` records skipped EVM transactions and advances the applied marker. A restart then skips this height because it is marked applied. This differs from the existing flush-worker behavior, which correctly latches a failure when its write fails.

There are similar conversions on the native path: session reads use `.ok().flatten()` at `app.rs:2001`, treating a storage fault as a missing session; nonce reads use `.unwrap_or(None)` at line 2092, treating a storage fault as an unused nonce. These outcomes depend on a node's local fault, not committed transaction bytes.

**Impact.** One replica can discard EVM effects, skip an authorized session action, or re-execute a consumed native nonce while healthy replicas execute normally. A later successful flush can make that difference durable. The state-hash monitor may detect divergence later, but its fail-stop is off by default; detection is not a substitute for preserving execution semantics at the fault.

**Regression test.** Inject a one-shot read error separately during EVM storage access, session lookup and nonce lookup. Require the execution failure latch, no applied-height advance and no partial state commit. After reopening without the injected error, replay must match the healthy reference.

**Recommended fix.** Keep deterministic user rejection separate from local infrastructure failure. Preserve typed errors through signature/session and nonce resolution, and stop execution before committing a marker whenever required state cannot be read.

## F05 Vote state is not synchronized before transmission

**Evidence.** The vote path correctly calls `set_vote_state_atomic` before sending (`crates/hotstuff_rs/src/hotstuff/implementation.rs:2763`). However, its RocksDB implementation at `crates/torus-consensus/src/kv_store.rs:170` calls ordinary `db.write(batch)` with default write options. Atomicity protects the two vote fields from partial batches; it does not synchronize the batch to persistent storage.

[RocksDB's primary documentation](https://github.com/facebook/rocksdb/wiki/Basic-Operations#synchronous-writes) distinguishes process termination from host crashes: default writes can be lost on a machine crash. The optional commit-boundary barrier at `app.rs:1020–1051` runs later, is off by default, and does not close the interval between sending a vote and any later commit. Enabling that toggle alone is insufficient for this finding.

**Impact.** After a host crash in that interval, a restarted validator may lose its recorded vote/lock progress and sign a different proposal in a view it already voted in. This creates an equivocation risk under crash recovery. The existing test that asserts write-before-send ordering does not test power-loss durability. No host crash experiment was performed here.

**Regression test.** First assert that all safety-critical vote paths request a synchronous durability barrier before their outbound message is released. Separately use a disposable VM or a storage fault model to test loss of unsynchronized WAL writes; `kill -9` alone does not model this.

**Recommended fix.** Synchronize the required lock and vote state before releasing a vote, or implement group commit with outbound votes held until its barrier succeeds. A failed barrier must prevent transmission.

## F06 ADL never advances beyond its first scan window

**Evidence.** `crates/torus-core/src/liquidation.rs:340` implements `adl_candidates`. Each call initializes `start` to an empty key at line 349 and walks at most `ADL_MAX_SCAN_ROWS = 65_536` rows across the global position column family. It filters market and side **after** consuming that row budget. `crates/torus-bridge/src/liquidation_step.rs:276` invokes this function afresh for each affected position.

The outer liquidation pass has a trader cursor, but it does not advance this inner counterparty scan. Pending-liquidation rows trigger more attempts; they also do not retain an ADL scan cursor.

**Counterexample.** Maintain 65,536 lower-key position rows in another market, with eligible opposite-side positions in the affected market beyond that prefix. Each retry scans the same unrelated rows, returns no eligible counterparties, and closes nothing. The attached model demonstrates three identical unsuccessful retries while an eligible counterparty exists. The prefix can also include ineligible same-side positions.

**Impact.** Bad debt and a bankrupt position can remain indefinitely unresolved despite available counterparties. The same restriction affects vault ADL. Bounded work per block is reasonable; a fixed prefix without eventual coverage is not a retry mechanism.

**Regression test.** Seed a balanced multi-market position fixture exceeding the cap, with all relevant ADL counterparties beyond the prefix. Across bounded liquidation steps, assert eventual closure and conservation of size/collateral. Also test restart continuity and stable ordering.

**Recommended fix.** Use a consensus-persisted scan cursor or an index by market and side, with explicit progress and wraparound rules. Specify how windowed scanning interacts with counterparty ranking; changing the window changes consensus-visible choices.

## F07 Header epochs freeze the fee transition

**Evidence.** The live CTE builder sets `epoch: parent_header.epoch` at `crates/torus-consensus/src/app.rs:5210`. Its synthetic genesis parent sets epoch zero (`crates/torus-bridge/src/proposer.rs:343`). The live builder never derives the child epoch from height, so ordinary descendants retain zero.

Native execution takes the header's epoch (`app.rs:2199` and line 2212). `crates/torus-bridge/src/native_executor.rs:8263` passes it to `RewardDistributor::distribute_block_fees`. The fee schedule in `crates/torus-economics/src/types.rs:362–374` intends a transition over 1,825 epochs, from 10/0/45/45 percent burn/validator/treasury/dev-pool to 25/25/25/25 percent.

**Impact.** Fee-paying blocks continue using epoch-zero ratios even while height-based validator rotation progresses. This finding does **not** mean validator rotation itself is stuck. An arbitrary proposer-supplied epoch is also not validated by the pre-vote header checks.

**Regression test.** Generate proposals through `build_proposal` across several epoch boundaries, execute fee-paying blocks, and compare recipient amounts against `EpochManager::epoch_for_block(height, epoch_length)`. The attached model shows the inheritance issue with epoch length four at height twelve.

**Recommended fix.** Derive the fee epoch from protocol height/configuration during execution and ensure the advertised header agrees. Any change to historical fee results needs an explicit activation/relaunch policy.

## Coverage and remaining validation

The review traced proposal/body checks, QC lock and vote persistence, post-commit execution, native signature/session/nonce handling, EVM fee/bundle accounting, journaled precompile calls, committed manifests and applied markers, resident overlays, oracle aggregation, liquidation/ADL and anti-spam admission/selection. It used Torus memory and code-index orientation, then checked the actual checkout; index freshness was not assumed.

Several older findings are addressed in this source: the Generic lock follows the justified parent and is monotonic; voting waits for body checks; native DA hashes bind signatures; caught EVM frame reverts have journal checkpoints; writer precompiles reject delegate/static calls; locally observed equivocation no longer directly slashes state; and block flushes generally include applied markers. These are source observations, not a fresh runtime certification of those fixes.

Additional areas deserve targeted adversarial tests before closing a whole-chain audit:

- The header vote phase uses the proposer-supplied `has_validator_set_updates` flag (`hotstuff/implementation.rs:2748`). Compare it to the application's actual validator-set plan, including a deliberately false flag at a transition. The resulting protocol impact was not established here.
- Check the relationship between HotStuff's outer block height and the Torus header height across every insertion/sync route. Hash integrity alone does not establish height continuity; commit-time guards need an adversarial test.
- Exercise public peer admission under sustained load. Network bridge ingress includes unbounded channels; this review did not establish a quantified remotely reachable memory-exhaustion case.
- Run the existing consensus model/checker, epoch-change partition tests, serial/pipelined state equivalence tests, and replay/crash suites against this exact commit. A source audit cannot establish BFT safety or performance under all schedules.

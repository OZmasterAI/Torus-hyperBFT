# Torus chain audit, third pass: consensus and recovery

Audited on 2026-10-04 on branch `merge/item6-sync2`, revision `cea1254e34625e6b09c58f794de8793b5c12713c`. This is an audit of current consensus, validator-transition, sync, and restart paths, not merely this branch's diff. Local identifiers C01/C02 avoid collisions with the first two reports' F01–F11.

**Two additional P1 high findings:** an unauthenticated validator-update hint can poison the persisted highest certificate and defeat automatic recovery; a selected Byzantine sync server can terminate an honest node with a block that was never certified.

This is a source audit. No Rust tests, real signatures/quorums, network fault schedule, or live-chain exploit were executed because Cargo and rustc are unavailable. Counterexamples below trace current production code and specify the regression to run when the toolchain is available. No production source, branch, Git index, external service, or installed toolchain was changed. These are source-supported findings requiring production-code regressions, not runtime reproduction or claims of observed deployed incidents.

## C01 A false Prepare hint on an ordinary block can strand automatic recovery

### Root cause and reachable paths

`ProposalHeader.has_validator_set_updates` is a wire-supplied boolean (`crates/hotstuff_rs/src/hotstuff/messages.rs:421`). Header integrity recomputes only `Block::hash(height, justify, data_hash)` (`crates/hotstuff_rs/src/hotstuff/implementation.rs:2213`); that hash excludes the boolean (`crates/hotstuff_rs/src/types/block.rs:73`). Body binding compares hash, height, data hash, and justify, also excluding the boolean (`implementation.rs:2826`). The header path's `cast_header_vote` selects Prepare when this hint is true, even when the held/validated body's actual application result contains no validator updates (`implementation.rs:2748`). Its final vote guards check view, voter eligibility, previous vote, and lock compatibility, without checking this hint against the application result (`implementation.rs:2740`). Unlike the full-proposal path at `implementation.rs:1472`, it does not derive the phase from `validator_set_updates`.

The distinction is a consensus invariant, not a cosmetic hint: `safe_pc` allows Prepare only for a block containing validator-set updates (`crates/hotstuff_rs/src/block_tree/invariants.rs:395`), while Generic requires no updates. But a collected certificate for a block in `pending_headers` or `pending_bodies` checks only the lock clause and skips this phase/update predicate (`implementation.rs:1718`, `implementation.rs:1730`). It then persists the certificate as highest PC and calls update (`implementation.rs:1743`). The pacemaker broadcasts highest PCs of every phase (`crates/hotstuff_rs/src/pacemaker/implementation.rs:194`). On receipt it checks `pc.is_correct`, then persists the remote highest PC without `safe_pc` or phase/update compatibility (`pacemaker/implementation.rs:474`, `pacemaker/implementation.rs:488`).

`PhaseCertificate::is_correct` does not independently close this gap. With no previous committed validator update it validates signatures for every phase (`crates/hotstuff_rs/src/hotstuff/types.rs:60`). After an earlier committed update, a certified block above that update height also gets only signature verification against the committed set (`types.rs:78`). The phase/update-status checks in this function apply to the last committed updating block's own height, not an ordinary later block. Choose the attack block at such a later height (or before any update), so the false Prepare certificate passes the pacemaker's actual admission predicate even once its body is in the tree.

### Finite-trigger counterexample

Use four equally weighted validators A, H1, H2, H3, with A Byzantine and scheduled to propose in view v. Let H1 be a vote recipient for v; phase votes are routed to the next leader and its backup (`implementation.rs:1201`, `crates/hotstuff_rs/src/hotstuff/roles.rs:159`). Choose an ordinary, application-valid block B extending a valid parent P, with **no** validator-set updates. All honest nodes know P and are able to vote in v.

1. A sends the valid header/body for B but sets `has_validator_set_updates=true`. H1 receives the header; briefly delay its B body. Its accepted header remains in `pending_headers` (`implementation.rs:2403`). Deliver complete B bodies to H2 and H3. Their pre-vote data checks return Held, and they sign Prepare because of the header boolean (`implementation.rs:2553`, `implementation.rs:2748`). They may then insert B as an ordinary block; this does not retract their signatures.
2. A contributes its own Prepare signature. Deliver these three votes to H1 while its header is pending and H1 is still in v. H1's collector forms a valid quorum certificate Q=(B,v,Prepare). H1's own vote is unnecessary: A+H2+H3 already meet the quorum. The pending-block bypass admits Q by lock compatibility, without checking that B updates validators (`implementation.rs:1718`). H1 persists Q as highest PC.
3. H1's pacemaker broadcasts Q; deliver it to the honest validators. Their signature-only admission accepts it and records it as highest PC. Deliver H1's previously delayed body, so all honest nodes now hold the same valid ordinary B. Neither B insertion nor the earlier parent certificate replaces the newer Q: highest-PC writes advance only to greater views (`crates/hotstuff_rs/src/block_tree/accessors/internal.rs:341`, `internal.rs:584`). A can now stop misbehaving, and the network can deliver every remaining message promptly.
4. In v+1, the honest leader chooses a Nudge because highest PC has Prepare phase (`implementation.rs:862`). Honest receivers reject it: B has no validator updates, so `safe_nudge`'s `safe_pc` test fails (`implementation.rs:1560`, `invariants.rs:439`). Thus it cannot form the Precommit/Commit/Decide progression.
5. In later views, `repropose_block` returns B whenever highest PC is Prepare and the current view is not Q.view+1 (`invariants.rs:686`). The leader unconditionally re-broadcasts B with the hint **true** (`implementation.rs:743`, `implementation.rs:756`). This happens before the TC-based recovery branch (`implementation.rs:767`). Every successful header vote is again Prepare; no honest header producer corrects the hint from B's actual status. If a newer Prepare QC forms, the next view again tries the rejected nudge; if no QC forms, stale-Prepare reproposal repeats. Neither case yields a Generic QC or completes phased progress.

The body delay is finite and affects only initial certificate admission. This does not assume an attacker can intercept arbitrary point-to-point votes or forge honest signatures: it uses the actual honest vote recipient's pending-header bypass. Leader authentication is satisfied because A is the scheduled proposer (`implementation.rs:1144`). Quorum intersection and lock-before-vote still hold; the finding is a liveness failure, not a demonstrated conflicting commit.

### Later guards and recovery checked

Full `safe_pc` checks correctly reject the wrong-phase Q once B's no-update status is available; this is precisely why nudges cannot progress. They do not remove the already persisted highest PC. NewView processing cannot downgrade it: the bad Q fails `safe_pc`, and older legitimate PCs do not pass the monotonic highest-view write. Header/body recovery fetches valid B successfully, so data recovery does not solve its incorrect phase. Block sync's terminal-certificate path also rejects Q through `safe_pc` (`crates/hotstuff_rs/src/block_sync/client.rs:572`); replaying older committed blocks does not replace the newer highest PC. All honest nodes in this schedule lack a later committed chain to sync from.

Restart selects views using persisted highest PC and highest entered view (`crates/hotstuff_rs/src/algorithm.rs:74`), retaining the same bad phase. In steady state the stale Prepare remains even after the transient pending header disappears. The repository's manual block-tree surgery can explicitly reset highest/locked PCs (`crates/hotstuff_rs/src/block_tree/recovery.rs:123`); that is an operator recovery mechanism, not an automatic protocol escape. Therefore the claim is persistent loss of automatic progress under the stated schedule, not irreparable database damage.

### Fix direction and regression

Determine Prepare/Generic from the held body's actual deterministic validator-update result before signing, and validate any advertised hint against that result. If a header needs to carry the result, bind it to certified block metadata and verify it against application semantics; simply hashing an attacker-selected boolean does not prove correctness. Treat a body-pending QC as provisional: it must not become an authoritative highest PC until its phase/update compatibility is known. Pacemaker admission needs the same compatibility policy, including a safe way to defer an unknown-body certificate and recheck it on insertion. Preserve legitimate header-first recovery and transition certificates.

Add a four-validator fault-schedule regression implementing steps 1–3 above, with only one Byzantine proposer and a bounded body delay at the next vote collector. After delivering the body and stopping faulty behavior, require every honest node to commit several new blocks without restart/surgery. Assert that the wrong Prepare QC is never an authoritative highest PC. Exercise both no previous update and B.height greater than the last updating block. Also vary the opposite hint on a real updating block, stored-body versus pending-body votes, full proposals, remote AdvanceView, and a restart at the poisoned frontier.

## C02 A Byzantine sync server can terminate a node with an uncertified block

### Root cause and admission order

Sync selects an eligible server after receiving its signed advertisement (`crates/hotstuff_rs/src/block_sync/client.rs:598`), choosing from registered servers at `client.rs:736`. Installed validators are eligible (`client.rs:1509`), so the stated attacker is a selected Byzantine validator, not an unauthenticated arbitrary network peer.

The worker accepts the selected peer's response and forwards its blocks and highest PC without checking response heights against the requested start/limit (`crates/hotstuff_rs/src/block_sync/worker.rs:111`). The receiver checks sender identity only (`crates/hotstuff_rs/src/networking/receiving.rs:473`). The algorithm checks each new block's `Block::is_correct` (`client.rs:416`). That validates its recomputed block hash and **its parent's** justify certificate (`crates/hotstuff_rs/src/types/block.rs:90`), not a certificate for this block, a commit proof for its ancestry, or the response's terminal certificate.

Immediately after that check, if the block's supplied height has a local committed hash different from this block's hash, sync calls `app.on_fatal_safety_violation()` (`client.rs:435`, `client.rs:453`). This precedes application validation (`client.rs:487`) and response highest-PC verification (`client.rs:540`, `client.rs:572`). Consequently a peer's assertion that it is serving a committed chain is treated as evidence that two honest quorums finalized conflicting blocks.

The production callback latches `exec_failed` (`crates/torus-consensus/src/app.rs:5596`), and the node's watcher exits with code 70 (`crates/torus-node/src/main.rs:792`, `main.rs:799`). This is an actual termination path, not only a log or peer blacklist.

### Counterexample and impact

Suppose the victim retains committed block C at height h. During a sync session with Byzantine validator A, the victim requests a range starting after h (or any other legitimate range). A returns a single block X at **h**, using C's already valid parent certificate, a different data hash, and a recomputed outer hash. Its body can be arbitrary because application validation has not run. X needs no signatures certifying X, no proposer authority for its original height, no quorum on a conflicting child, and no actual fork. Give the response an irrelevant/invalid terminal certificate if desired; that is checked later.

`Block::is_correct(X)` passes the reviewed hash/parent-signature predicate. X differs from C at the same numeric height, so the victim's fatal callback runs and the node exits. Returning a different height than requested is not screened by the worker/client path. The attack does not rely on F08's ability to certify skipped heights: h is simply an already committed numeric slot used to trigger the comparison.

An even simpler source witness is already in the repository: `committed_conflict_invokes_fatal_callback` deliberately constructs `Block::new(height=5, genesis_pc(), arbitrary data_hash, empty data)` (`client.rs:1709`) and asserts that the fatal callback runs (`client.rs:1734`). That fixture establishes the implemented ordering and predicate, but its own description of an uncertified genesis-justified block as a "conflicting committed chain" is unjustified. This test was read, not executed during this audit.

One selected malicious server can terminate each syncing victim it serves. Repeating the attack after supervisor restart can keep victims unavailable; automatic peer selection is a substantive prerequisite, so this report does not claim guaranteed instantaneous termination of every node on a healthy non-syncing network. Rejecting genuinely conflicting certified history remains valuable; its proof requirement is missing here.

### Fix direction and regression

Validate response range/order, parent connectivity, application/body integrity, and appropriate certificates before drawing finality conclusions. An uncertified conflicting block from a server should fail the session and penalize that server without globally halting the victim. If halting on conflicting finalized history is the policy, require a cryptographically verified commit proof that actually commits the conflicting block under the correct historical validator set; a parent's QC or the server's authenticated identity is insufficient. A terminal QC that merely exists elsewhere in the response is also insufficient without the certified ancestry and protocol commit rule.

Add a regression with a genuinely seeded committed C and active sync request for h+1. Return a hash-correct sibling X at h carrying C's valid parent QC but no QC on X, with an invalid response highest PC. Require session rejection/peer penalty, **no fatal callback**, and continued voting. Include the genesis-justified fixture, an invalid body, out-of-range and unordered responses, a correctly re-served C, and a real contradictory commit proof for the desired fatal policy. Verify the callback boundary independently from process-exit integration.

## Coverage, guards, and remaining leads

Reviewed header/full-proposal voting and body binding; phase collectors and signature-set selection; lock and two-chain commit predicates; validator-update status and phased recovery; pacemaker highest-PC admission and TC recovery; sync request/worker/response/canonical stored-block paths; startup view selection; manual block-tree recovery; and Torus application data checks and fatal callback. Existing F01–F11 were treated as prior findings and were not renumbered as new discoveries.

Several relevant protections are present: the header verifies its scheduled proposer; header votes require body/data availability; lock-before-vote and monotonic lock advancement constrain conflicting branches; known sync blocks are re-driven from local canonical metadata; and sync terminal highest PC uses `safe_pc`. C01/C02 identify specific gaps despite these guards, not their absence generally. Reputation-based leader selection is default off with an explicit source explanation of its divergent-local-history risk (`pacemaker/implementation.rs:1125`); that historical concern is not reported as a new default-path finding.

Two leads remain unpromoted: TC-based proposal replays hard-code `has_validator_set_updates=false` (`implementation.rs:773`, `implementation.rs:1977`), but an exclusively honest updating-block timeout schedule needs to account for the preceding stale Prepare/Precommit reproposal path; and timeout certificates verify signed per-voter hash summaries but do not independently establish that aggregate `high_tip`, its view/metadata, `high_qc`, and `high_tip_is_winner` derive from those summaries (`crates/hotstuff_rs/src/pacemaker/types.rs:87`). Later parent/certificate/lock guards constrain impact, so neither lead is labeled a proven safety violation or a third finding here.

No exhaustive weighted validator-transition model, real fault-injected restart, signature simulation, Rust build, or live-network test was performed. Parent agent will consolidate numbering and save Torus discoveries to avoid duplicate shared-memory records.

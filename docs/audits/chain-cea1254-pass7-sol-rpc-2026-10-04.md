## Q01 — P2: wallet query commands do not consume the shipped node schema

The ordinary `Positions` dispatch calls `cmd_positions` (`tools/wallet/src/main.rs:404–412`). That command fetches `torus_getMarkets` and searches each row for numeric `market_id` or numeric `id` (`tools/wallet/src/commands/query.rs:260–270`). The actual node returns `RpcMarketInfo` with camelCase keys (`crates/torus-rpc/src/types.rs:310–318`), populated with `market_id: hex_u64(mid)` (`crates/torus-rpc/src/torus.rs:1105–1106`). Thus a normal row such as `{"marketId":"0x1",...}` has neither accepted key. Every row is skipped before any position request; both human and JSON output report no positions, even for a trader with an open listed-market position. This is distinct from the previously documented wallet `result:null` problem: this failure occurs while parsing the non-null market-list result.

The same manually assumed schema causes related wrong human output:

- `Validators` reads `power` as JSON u64 and `commission_bps` (`query.rs:63–67`); the node emits hexadecimal string `power` and camelCase `commissionBps` (`types.rs:471–482`, `torus.rs:1284–1290`). Nonzero stake/power and commission display as zero. JSON mode returns the original response before this formatting branch (`query.rs:50–52`).
- `Epoch` expects numeric `epoch`, `start_block`, `end_block`, and `blocks_remaining` (`query.rs:322–329`). The server emits hex string `currentEpoch`, `epochStartBlock`, `epochEndBlock`, and `blocksRemaining` (`types.rs:485–494`, `torus.rs:1303–1309`). Human output is `Epoch 0  blocks 0-0  0 remaining`; JSON mode preserves the response.
- `Balance` human native formatting looks for `spot` and `perp` (`query.rs:31–43`), absent from `RpcBalances` (`types.rs:288–296`), so it omits the actual native balance fields. Its raw native JSON response remains available in JSON mode.

Useful regression: serialize actual node response types into a mock HTTP server, invoke wallet queries, and assert populated Positions, nonzero validator power/commission, epoch timing, and native balance output. Assert the position RPC receives the original hex market identifier. Simply replacing the key then calling `mid.to_string()` (`query.rs:272`) would introduce another error for IDs >=10: node `parse_u64` interprets unprefixed strings as hexadecimal (`types.rs:83–85`). Preserve the wire identifier or explicitly re-encode hex. Enumerate all market pages too: the current command asks for one default page; node default limit is 100 (`torus.rs:1070–1073`). Existing wallet RPC tests (`tools/wallet/src/rpc.rs:226–256`) cover formatting/parsing helpers, not these node-to-command schema contracts. They were read, not executed.

## Q02 — P2: accepted Ethereum log subscriptions have no shipped production publisher

`BlockNotifier` publicly owns `new_logs`, creates its broadcast channel, and is passed into the node's RPC server (`crates/torus-rpc/src/lib.rs:118–151`; `crates/torus-node/src/main.rs:867–873,980–989`). `eth_subscribe("logs", filter)` accepts the subscription and waits on that receiver (`crates/torus-rpc/src/eth.rs:1227,1250–1289`). Whole-source search across `crates/**/*.rs` finds **no `new_logs.send` or other production publication to this channel**. The node's commit callback publishes only heads (`main.rs:958–970`), while the application execution callback emits trading `BlockFills` through the separately installed fill sink (`main.rs:873`; `crates/torus-consensus/src/app.rs:2611`; `rpc/lib.rs:169–190`). That fill path does not feed EVM logs.

Consequently, a legitimate contract transaction can execute and have logs available through receipt/getLogs retrieval, while an accepted `eth_subscribe("logs")` receives none in the shipped node. This claim is limited to the checked-out binary wiring; an external embedding application could access the public channel and publish its own events. No live notification failure was reproduced. This was not found in the reviewed F01–F31 or September audit tables.

Additional lifecycle evidence for the same accepted-but-idle subscription: the Ethereum subscription task only observes `rx.recv()` and decrements the shared count after its loop exits (`eth.rs:1256,1287–1289`), without selecting `sink.closed()`. With no publisher, a client disconnect/unsubscribe does not wake that loop; its global active-subscription slot can remain retained for the server lifetime. `newHeads` and pending subscriptions similarly release only on a later received event/send failure (`eth.rs:1233–1247,1295–1311`). This differs from the existing Torus trade subscription, which acquires an RAII slot, subscribes before accept, and selects sink closure (`torus.rs:2016–2046`, `:2089–2098`). That current trade safeguard must not be called absent.

Useful regression: through the actual node/application execution-to-notifier path, subscribe, execute a normal log-emitting contract transaction, then require exactly the receipt's logs with matching block/hash/transaction/log indices. Unsubscribe and disconnect without another transaction/block and require `active_subscriptions` to return to its prior value. Test Ethereum `newHeads` and pending subscriptions with the same quiet disconnect case. The current `ws_subscriptions_capped_per_connection` test (`rpc/lib.rs:2436`) checks per-connection admission limits, not idle-task cleanup or EVM log publication; synthetic direct notifier sends would not prove production wiring.

If publication is added, a further assertion is necessary: the `logs` subscription currently copies only `filter.address` (`eth.rs:1251–1253`) and never applies `filter.topics`, unlike getLogs (`eth.rs:1115`). Treat that as a visible implementation gap of the presently dormant path, not a third independently observed delivery failure.

## Qualifications of earlier RPC/explorer statements

**Applied frontier exists now.** `eth_head` reads the durable applied marker and caps it by committed height (`eth.rs:176–179`); `eth_header` hides a stored block above that frontier (`:183–188`). Block/transaction-count projections enumerate receipts, giving executed transactions dense Ethereum indices and excluding skipped transactions (`:225–242,447–472,873,902,931–945`). The existing `eth_views_list_only_executed_evm_txs` test (`rpc/lib.rs:3200–3425`) executes success/skipped/revert through the bridge and checks dense transaction indices and null views for an unexecuted block. This refutes the broad historical description that all current Ethereum block queries always publish committed-but-unexecuted transaction lists. The test manually installs application status/applied-marker records; it does not verify the full application's atomic frontier write under faults.

**Historical state/snapshot binding remains narrower and unresolved.** Balance/code/storage/nonce handlers still resolve selectors into unused variables and read current state (`eth.rs:617–682`), so historical selector semantics remain a prior Astra issue. Call/estimate now choose an applied-height header (`eth.rs:965–988,1012–1031`), but still execute against the live `StateDb` and estimation repeats probes (`:996–998,1045–1065`). An applied frontier alone does not pin a RocksDB snapshot across concurrent execution. The ignored request gas ceiling (`:1032–1043`), fee-history placeholder gas ratios/future header behavior (`:1153–1196`), missing blockHash log selector (`types.rs:235–242`), and type-2 gasPrice fallback remain earlier candidates, not new findings.

**getLogs future ranges still require a precise completeness contract.** The source scans only `from..=to.min(latest)` (`eth.rs:1092–1096`). This removes committed-but-unexecuted heights from the scanned portion, but it does not reject an explicitly requested upper bound above the current applied head. A request spanning the current head and a future height can still succeed with only the present prefix, then acquire later logs on repetition. The comment that a range “never comes back short and later fills in” (`:1092–1094`) is too broad. This is a qualification/remaining consequence of the historical false-completeness issue, not separately numbered. Add exact-bound assertions distinguishing latest-relative queries from fixed future-ended ranges.

**Explorer reconciliation runs on subsequent heads now.** Every received head rescans `pending_range` and indexes from its cursor through the current applied head (`indexer.rs:241–253`). That repairs a clean missed-height interval on the next notification. Historical descriptions of no gap reconciliation must therefore specify startup/reconnect timing and failed/partial indexing: F26's early same-hash skip and cursor advance still prevent repair of partial rows (`:71–88,157–159`). The existing skipped-tx test checks executed/body indices and preserves a prior successful hash against a skipped replay (`indexer.rs:523–601`); it does not test transient failures/reconnection.

A normal quiet-tail race remains: the node sends the final head at commit (`node/main.rs:958–970`), explorer immediately samples applied head H-1, execution subsequently applies H, and there is no later commit notification. The loop has no polling timer, application-completion wakeup, or initial post-subscribe reconciliation (`explorer/indexer.rs:228–260`; `explorer/main.rs:28–43`). H stays absent from the explorer until another head, restart/backfill, or other explicit indexing. Reconnect also does not sample pending_range until the next head arrives. This is a bounded residual of the historical explorer subscription gap, **not a new numbered defect**; continued block production usually repairs it. Regress delayed final application followed by quiet time, and a block applied between initial backfill and subscription establishment, without relying on a later unrelated head to complete indexing.

## Missing receipt/log regression assertions

Existing getLogs filtering test (`rpc/lib.rs:3519–3562`) stores one receipt containing one log; the dense-index test has success/skipped/revert but no emitted-log assertions. A stronger source-level regression should execute multiple real logs around a skipped transaction, include a nonmatching log before a matching one, and compare full block transaction indices, by-index/by-hash views, receipt cumulative gas, and getLogs transactionIndex/logIndex.

## C4 L1 eligibility and valuation

The liquidation pass constructs its step marks from listed markets and calls
[`l1_on`](https://github.com/OZmasterAI/Torus-hyperBFT/blob/0a255607dbe2227ee47b70638b0198b80eaeb3cd/crates/torus-bridge/src/liquidation_step.rs#L145)
before using the sums cache. L1 requires both resident sums and a block mark
table, and turns off if the table contains any usable mark for a delisted
market. This guard matters because the general account reader can value all
markets in that table, while liquidation deliberately marks only listed
markets. The table builder includes aggregate rows, including still-fresh
rows for delisted markets; if the aggregate scan fails or the table is absent,
L1 is off.

When enabled, [`liq_view`](https://github.com/OZmasterAI/Torus-hyperBFT/blob/0a255607dbe2227ee47b70638b0198b80eaeb3cd/crates/torus-bridge/src/liquidation_step.rs#L165)
gets position sums through the same `AccountView::build` path used by C3,
returns `None` for isolated positions, no marked positions, or arithmetic
overflow, and reads the current balance separately. Those conditions match
the reference walk's eligibility and valuation behavior. Dirty position
prefixes bypass cached sums through `layer_touches`; unchanged traders use a
memo or version-matched entry. The [block mark table](https://github.com/OZmasterAI/Torus-hyperBFT/blob/0a255607dbe2227ee47b70638b0198b80eaeb3cd/crates/torus-bridge/src/native_executor.rs#L930)
and [C3 cache lifecycle](https://github.com/OZmasterAI/Torus-hyperBFT/blob/0a255607dbe2227ee47b70638b0198b80eaeb3cd/crates/torus-bridge/src/native_executor.rs#L885)
remain the same assumptions described in pass 15.

The cache is used in the initial classification, repeated Stage 1 health
checks, post-liquidation pending calculation, and the liquidator-vault check.
The execution caller still runs the liquidation step after CoreWriter and
fail-stops if the step records a fatal storage error; C4 does not move the
liquidation phase relative to governance or fee distribution.

## Checked-in coverage and its limits

The new [`liquidation_l1_tests.rs`](https://github.com/OZmasterAI/Torus-hyperBFT/blob/0a255607dbe2227ee47b70638b0198b80eaeb3cd/crates/torus-bridge/src/liquidation_l1_tests.rs#L1)
defines six seeded 60-block comparisons between L1 and the reference walk.
Its cases include resident-row reuse, parent overlays, mark changes and
absence, delisting, isolated positions, cursor cuts, Stage 1, backstop and
ADL. Assertions compare liquidation outputs, liquidation/position/balance
rows and trigger counts, with shadow comparisons for each L1 valuation. The
storage-read integration tests also assert the intended scan reduction for
changing and fixed marks. These are inspected test definitions; they were not
executed in this review. They do not establish full-node signed-block
equivalence, crash recovery, durable database reopen behavior or performance
on the merged head.

# R01 fault test on a real node (ozarchy s34, 2026-10-09)

Binary: release build of `fix/r01-write-fail-stop` `01d991ab` (own target dir). Devnet: 4 validators
on one host; v3's data dir on a 4 GiB ext4 loop fs (`/mnt/r01`), the other three on the root fs, so
3 of 4 stay live and v3's running state hash can be compared with theirs after it rejoins. Fault:
fill `/mnt/r01` with `fallocate` while v3 runs; clear by deleting the fill file, then restart v3.
Every write error was `No space left on device` on a RocksDB WAL append. Harness:
`tools/r01-fault/` (paths are ozarchy's; `run-case.sh`, `check-hashes.sh`, `ro-case.sh`).

| 1: pipeline off, native | 924 | 80 native, 0 EVM | 70 | 923 | 3 blocks (committed 926) | equal at 900, 1000 (100-1500 all equal) |

| 3: pipeline on, epoch boundary, empty | 2220 | empty, serial at the boundary | 70 | 2219 | 8 blocks | equal at 2200, 2300 |

Marker after exit = `applied_height` in the restart's `crash recovery: execution gap detected` line.
First failing write: case 1 and 3-empty the block's state + marker flush (`FATAL: native overlay
flush + applied-height marker failed`); case 2 the consensus write first, then the marker-only flush
(`FATAL: applied-height marker flush failed`); case 3-native the order-body (DA) store first, then
the boundary flush. Per case: `results/<case>/attempts.txt`, `v*.log`, `events.log` on ozarchy
(`/home/oz/r01-fault/results/`: `c1d-pipeoff-native-heavy`, `c2b-pipeoff-empty-starve`,
`c3-pipeon-boundary-native`, `c3b-pipeon-boundary-empty`).

## Finding outside R01's scope: a full disk usually leaves a live node that no longer works (no exit 70)

With 0-2% execution load (the natural shape), **all 15 empty-block fills and 4 of 4 light-native
fills hung instead of exiting** (`results/c1-pipeoff-native`, `c2-pipeoff-empty`, ... `ZOMBIE
exit=alive`):

1. a consensus write (`crates/torus-consensus/src/kv_store.rs:170`,
   `self.db.write(batch).expect("RocksDB write failed")`) or the native DA store batch write
   (`torus_mempool: native DA store batch write failed`) fails first; RocksDB then refuses all writes;
2. the `hotstuff-algo` thread panics at `kv_store.rs:170:30`; the process keeps running;
3. the execution loop sees its channel close, logs "shutting down" and does not set the fail-stop
   latch;
4. the node stayed up > 3.5 min with RPC answering and the applied marker frozen.

Exit 70 happened only when a committed block was still executing when writes began to fail; the
passes above needed heavy native load (400 orders x 10 actions/s per sender) or a starved
`torus-execution` thread (SCHED_IDLE next to busy loops on one CPU). R01's fix is correct for the
paths it covers; the gap is that a consensus-thread panic (and the DA store write error) do not
reach the same node-wide fail-stop. Candidate fix (not built): latch the fail-stop / exit 70 on a
`hotstuff-algo` panic (or turn the `expect` into an error the consensus loop surfaces), and treat an
execution-loop channel close without a clean shutdown as a fail-stop.

## Read-only case (run 05:45, `ro-native-1`)

Forced ext4 error on `/mnt/r01` (`errors=remount-ro`, then `/sys/fs/ext4/loop0/trigger_fs_error`;
the kernel aborted the journal and remounted read-only, `emergency_ro`), pipeline off, native load,
starved `torus-execution` thread (`STARVE=1`, see the full-disk finding). Steps:
`tools/r01-fault/RO-STEPS.md`.

| H | first failing write | R01 line | exit | last applied (RPC) before exit | boot replay | checkpoint hashes v0-v3 |
|---|---|---|---|---|---|---|
| 676 | native DA store WAL append (EROFS) | `FATAL: native overlay flush + applied-height marker failed ... height=676 has_evm=false` | 70 | 675 (H-1) | `committed_height=667 applied_height=635 gap=32` | equal at 400-800 |

The durable marker after umount / `e2fsck` / mount is 635, below the 675 the node reported before it
exited: the journal abort drops writes that were only in the page cache (RocksDB WAL appends are not
fsynced per write), so the on-disk state falls back to the last synced point, like a power loss;
consensus' committed height falls back too (667). The restart replays 32 blocks and catches up
from the peers; the running hash equals the peers' at every checkpoint 400-800. The empty-block
read-only case was not run (the full-disk light-load finding above predicts a hang there).

## R01b re-run: light-load full disk now exits 70 (ozarchy, 2026-10-09 17:15-17:25)

Binary: release build of `main` `d2b2736b` (R01b thread fail-stop + latch-before-write `184828c1`),
md5 `6efff7f212e08db001542379d364be96`, own target dir. The harness is unchanged except `NODE_BIN`/`WT`
in `lib.sh`; the native load tool is still the R01 `bench-throughput` built at `edc5adb7`. Steps:
`docs/audits/r01b-fault-steps.md` (steps 3, 4 and optional 5), `MAX_ATTEMPTS=5`, `WARM_S=60`, epoch 100.
Per case: `r01-fault-results/<case>-SUMMARY.txt`, `-attempts.txt`, `-hash-compare.txt`
(summaries made by `tools/r01-fault/r01b-summarize.sh`).

| case | attempts | exit | first FATAL line | exit after fill | marker at exit / H | restart | checkpoint hashes v0-v3 |
|---|---|---|---|---|---|---|---|
| 3: pipeline off, empty | 1/1 HIT | 70 | `FATAL: hotstuff-algo thread panicked (kv_store.rs:187 RocksDB write failed ... No space left)` | < 1 s | 1272 / 1273 | replays from 1273, rejoins | equal 100-1500 |
| 4: pipeline off, native | 1/1 HIT | 70 | `FATAL: native DA store writes keep failing — latching fail-stop in_a_row=3` | < 1 s (0.57 s after first ENOSPC) | 948 / 949 | replays from 949, rejoins | equal 100-1200 |
| 5: pipeline on, empty | 1/1 HIT | 70 | `FATAL: hotstuff-algo thread panicked (kv_store.rs:187 ...)` | < 1 s | 1182 / 1183 | replays from 1183, rejoins | equal 100-1400 |
| 5: pipeline on, native | 1/1 HIT | 70 | `FATAL: native DA store writes keep failing — latching fail-stop in_a_row=3` | < 1 s (0.67 s after first ENOSPC) | 1009 / 1010 | replays from 1010, rejoins | equal 100-1400 |

All four cases pass every criterion in the steps doc. Each one was a HIT with exit 70 on its first attempt, so no
ZOMBIE and no other exit code (R01 hung 15 of 15 empty and 4 of 4 light-native runs). No FATAL or panic line
appears on v3 before the fill, after the restart with free disk, or in the `check-hashes.sh` restart, and v0-v2
logged no FATAL. Hashes were compared twice per case: `run-case.sh` right after the restart, then
`check-hashes.sh` restarting all 4 validators on their data dirs.

Notes:
- **H and the marker.** In all four cases no block was executing when v3 died. The fault hit a consensus write
  (empty blocks) or the native DA store (native load) between blocks. So H is the next height to apply: the first
  block the restart executes. The marker at exit is the last `block done` height before the fault. On restart there
  was no `crash recovery: execution gap` line (committed = applied), and the first block executed was marker + 1.
  The marker is therefore H-1 in every case.
- **The harness's H is empty.** `run-case.sh` reads `height=` from the WANT line, and the R01b FATAL lines carry no
  height. As a result `failed-height.txt` and `block-H-body-from-v0.json` are empty, and the events log says `H=`.
  H above comes from the v3 log instead.
- **The DA path logs three FATAL lines.** In order: the latch, then `FATAL: execution pipeline has died` (+160 /
  +220 ms), then either the `hotstuff-algo` panic hook (case 4, +235 ms after the latch) or a 4th DA failure (case 5
  native, +282 ms). So the process exits about 250-300 ms after the latch, slightly above the doc's "~250 ms", and
  well inside the 20 s window.
- **Pipeline on is a single run.** Step 5 ran with the same `MAX_ATTEMPTS=5`; both cases were HITs on attempt 1.

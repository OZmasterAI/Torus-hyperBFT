## View cycle, load window (gap_attr.py view_join, mean ms)

Leader L proposes view v, collector N (leader of v+1) assembles its PC.
`cycle` = L's StartView(v) -> N's StartView(v+1). 394 / 412 views joined.

| segment | r1 | r2 |
|---|---|---|
| L StartView -> Propose | 340 | 347 |
| Propose -> last vote sent | 114 | 102 |
| last vote sent -> PC at N | 80 | 84 |
| of which: last vote admitted at N -> PC (algo queue) | 53 | 59 |
| PC -> N StartView(v+1) | 158 | 160 |
| of which: PC -> N's own AdvanceView admitted (commit feed + broadcast) | 73 | 82 |
| of which: own AdvanceView admitted -> StartView (loopback queue) | 84 | 78 |
| cycle | 692 | 693 |

Medians are far below means (vote queue p50 4 ms, p90 ~195 ms; loopback p50
~17 ms, p90 ~250 ms): the cost sits in tail views where the algo thread's
inbound queue is backed up.

Leader propose (load-window histograms, per node): build (StartView -> own
insert) 242-315, finalize (insert -> Propose) 65-124; produce_block 139-197
(select 79-91, mirror 44-101, attest ~9, parent/encode ~1). The build rest
(~110-120 ms) is the parent-body wait plus the block-tree write.

## Findings

1. The next leader's commit feed (process_update_result before the
   AdvanceView broadcast) costs ~78 ms/view (~11 %). Real, not dominant.
2. The collector enters v+1 only via an AdvanceView: its own broadcast,
   looped back through swarm admission -> inbound queue -> poller -> algo.
   The pacemaker changes view only on timeout (pacemaker/implementation.rs
   :174), a collected TC (:435) or a received AdvanceView (:531); the CollectPC
   path never calls update_view. Cost ~80 ms/view mean. Identified in 100 % of
   views by matching N's looped-back header key.
3. Leader propose is half the cycle (~345 ms): produce_block ~160, parent-body
   wait + tree write ~115, finalize ~100.

## Next

- Direct view entry on the collector after its own generic PC (removes the
  loopback, ~80 ms mean, larger in the tail). Needs a safety review: same PC
  as the broadcast, so the view change is what the loopback would do anyway.
- Broadcast AdvanceView before process_update_result (the commit feed then
  overlaps the transit instead of preceding it).
- Tail views: find what backs up the algo queue (body inserts / validate on
  the algo thread), since medians are small.

(ms, load-window means; cycle/propose from the view join, propose_build and

The mechanism works (qc_to_advance -45 to -70 ms), but the saving moves into
the next leader's propose: propose_build +55 ms with produce_block unchanged
(~134 ms), i.e. the collector now waits longer for the parent body before it
can build. The loopback was hiding that wait, not adding to it. Cycle is not
shorter and throughput is lower in both pairs (on 68.5k vs off 74.3k, native
blk/s 1.16 vs 1.28; 2/2 pairs, sign test p=0.25). Leader timeouts slightly
higher on (26/23 vs 21/19). Not adopted.

The next leader's binding constraint is the parent body: insert_persist
(proposal arrival -> body validated and written) ~170-184 ms against a vote
gather of ~105 ms. validate_block is ~57 ms (DA reconstruct ~48, attest ~11);
the remaining ~115 ms is body delivery, queueing and the write.

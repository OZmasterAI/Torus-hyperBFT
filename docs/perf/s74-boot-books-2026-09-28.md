# s74: restarted-node startup profile and parallel book load

## Startup profile

After the database opens (about 7–8 s with the 512 MiB WAL cap), a restarted
node replays the 2–6 blocks that were committed but not yet executed at the
kill. It does this before networking starts. Networking starts 6.7–9.8 s
after the database opens (s74-rv crash cells).

The first replayed block costs 5.1–6.5 s; each later block costs 0.5–1.5 s.
The difference is `torus_exec_load_books_seconds` at 4.3–4.7 s: the cold
rebuild of the resident order books (about 1.0M resting orders at the 60 s
kill).

## Change

- **ae392a0:** `LoadTimings`. The level-authority loader reports its root-CF
  scan, order-row store scan, rebuild and verify phases. It logs one line
  per load (`load_books: order books loaded from DB`) and keeps the numbers on
  `NativeExecContext::load_timings`. Also adds the release µbench
  `tests/load_books_ubench.rs`.
- **d6528ec:** each market's rebuild and boot verify now runs on scoped worker
  threads.
  - Markets are assigned by row count, heaviest first (LPT, the save-drain
    idiom).
  - Results are consumed in ascending market order, so the books and the
    first fatal error match the serial loop exactly.
  - `TORUS_LOAD_BOOKS_WORKERS` follows the same policy as
    `TORUS_SAVE_BOOKS_WORKERS`: unset uses the host thread count, `1` is
    serial.
- **Tests:** books are byte-identical for 2, 3, 4, 9 and 16 workers in modes
  2 and 3. A store corrupt in markets 3 and 7 reports market 3 for every
  worker count.
- **Test results:** torus-bridge 247 passed; workspace 1,869 passed, 0 failed.

## Results

**µbench** (release; 10 markets × 100k resting bids over 400 levels):

| | serial | parallel (18 threads) |
|---|---|---|
| store scan | 0.93–1.66 s | 1.03–1.40 s |
| rebuild + verify (wall) | 2.28–2.35 s | 0.33–0.48 s |
| total | 3.23–3.95 s | 1.49–1.79 s |

**Crash cells** (campaign `~/bench-results-matched/s74-bb-20260928`, frozen
node sha 42f7b058, n=1 per arm, `--crash-at 60`):

| | serial `=1` | parallel (default, 10 workers) |
|---|---|---|
| resting orders | 1.13M | 1.30M |
| store scan | 1,407 ms | 2,073 ms |
| rebuild + verify (wall) | 3,098 ms | 984 ms |
| load_books total | 4,507 ms | 3,077 ms |
| first replayed block | 5.64 s | 4.08 s |
| agreement / crash gate | AGREE / PASS | AGREE / PASS |

In vivo the parallel phase is 3× faster, against 6× in the µbench, because
the host is saturated during a cell. The single-threaded store scan
(1.4–2.1 s) is now the largest phase.

The warm (no-crash) cell on this build matched 68.4k/s, inside the usual
spread. The freeze was not scored at n=1: it varied from 15 to 75 s, driven
by a post-rejoin stall on one view (see below).

## Follow-ups

- **Post-rejoin stall.** Freezes of 31–75 s occur when the chain waits out
  one view's backed-off timeout after the rejoin. The next investigation is
  to find which vote or message is missing.
- **Store scan.** It needs a range-scan backend API to split it per market.
- **Start networking before the replay**, or replay asynchronously.
